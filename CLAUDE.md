## Project

Aemotional-Line: a deliberately slow, structured messaging system for couples, supervised by a couples therapist (paid version) — a free public version without therapist/archive is planned as a separate app. The full spec is an Italian design document ("Aemotional-Line - documento di progetto"); code and identifiers are in English, commit messages are often in Italian/English mix.

Planned stack (per spec, with Spring Data JDBC instead of JPA and MariaDB, decided 2026-10-30): Spring Boot REST backend + Spring Data JDBC on MariaDB, React + Vite + React Router + Bootstrap frontend. **Current state: the domain model** (`com.aemotionalline.domain`) **and the persistence layer** (`com.aemotionalline.infrastructure.persistence`: Spring Data JDBC and explicit SQL on MariaDB, Flyway schema in `src/main/resources/db/migration`, tests on a MariaDB Testcontainer: Docker must be running for the Spring tests) **and the application layer** (`com.aemotionalline.application`: one service per area, membership checks, views with closed envelopes) **and the security layer** (accounts, couple invitations, one-time links, Spring Security with sessions in MariaDB, the login and account endpoints under `/api/auth`, hardened cookies and headers; operator guide in `docs/deployment.md`) **are complete.** No other REST controllers and no frontend yet.

## Domain architecture

The domain layer is plain Java (should not depend on Spring) and throws `DomainException` for every rule violation (one type, so the future REST layer can map all of them to one client error). IDs are small records wrapping a `UUID` (`UserId`, `CoupleId`, `ConversationId`, `NegotiationId`, `ProposalId`, `MessageId`, `ParagraphId`; each has `random()` so the domain creates its own ids, time-ordered UUID v7 from `UuidV7`), except `DiscussionId(ConversationId conversationId, int discussionNumber)`, whose number is the readable position of the discussion (0, 1, 2…). Tests build deterministic ids with the test helper `Ids` (`Ids.user(10L)`, `Ids.paragraph(1L)`…, same number = same id). Tests live in mirrored packages under `src/test/java/com/aemotionalline/domain/` and construct aggregates directly (no Spring context), passing a `Clock` where time matters.

Key concepts and how they connect:

- **Couple** — two partners + one therapist. Most rules gate on `isPartner` / `isTherapist`.
- **Negotiation / Proposal** (`domain.negotiation`) — the "stipula" of the agreement (accordo): partners alternate turns (`currentResponder`) sending edited `Proposal` text + justification. `NegotiationStatus` (the request to talk is accepted/refused) is separate from `ProposalStatus` (the agreement text is accepted). Every sent proposal is kept in `ProposalArchive`; a conversation requires an accepted negotiation whose last proposal is accepted.
- **Conversation** (`domain.conversation`) — aggregate root. Created via `Conversation.start(id, couple, negotiation, clock)`, which opens the first `Discussion` and sets the agreement; the `Clock` gives every instant the conversation records (message sent, message read, negotiation archived, constraint request proposed/closed), so the caller can't fake time. Holds the `ConversationGraph`, the `ConstraintSet`, the negotiation history (`getNegotiationHistory()`, ordered `NegotiationRecord`s with the purpose of each negotiation and its sent proposals), the failed negotiations (`recordFailedNegotiation`, `getFailedNegotiations()`), the constraint change requests (`getConstraintRequestHistory()`), and the set of `Discussion`s. `openDiscussion(negotiation)` creates a new discussion; `openDiscussion(negotiation, originParagraphId)` creates one that expands a paragraph already sent (the spec's "discorso specifico", first step: see "Paragraph link rules"); `modifyAgreement(negotiation)` replaces the agreement. Discussion numbers are the count of discussions (0, 1, 2, no gaps even when the agreement changes in between).
- **Discussion** — an ordered list of `Message`s; enforces turn-taking (the same user cannot send twice without a reply, via `setLastSender`). Optionally has an origin paragraph (`getOriginParagraphId()`): the paragraph whose topic it expands. A specific discussion can be closed, never by one partner alone (closing request accepted by the other, or a special request confirmed by the therapist after a failed attempt); a closed discussion accepts no messages and each partner declares `RESOLVED` or `STALLED` with a reason (`getClosingRequests()`, `getTherapistClosingRequests()`, `getClosure()`).
- **Message / Paragraph** (`domain.message`) — messages are lists of paragraphs; no attachments. `Paragraph` is abstract with `SimpleParagraph`, `QuestionParagraph`, `PointedParagraph`, each with its own title/subtitle/body length limits; a POINTED answers exactly one question, given to its constructor (`new PointedParagraph(id, question, body)`, typed `QuestionParagraph`), and its title is computed as `In risposta a «question title»`; who may answer a question is decided in `Conversation.sendMessage` (only a POINTED, except in the first message of a discussion that expands that question). Two kinds of link: **references** (`addReference`/`getReferences`, rebuild the conversation) and **self-citations** (`addSelfCitation`/`getSelfCitations`, a link to the sender's own earlier paragraph, ignored by the graph and `Analyzer`). `Message.seal(skippedQuestions)`, called by `sendMessage`, makes the message and its paragraphs read-only and records, once, the questions of the answered message that it left unanswered (`getQuestionsLeftUnanswered()`).
- **ConversationGraph** — flat list of every sent paragraph; edges are `Paragraph.references` pointing from a reply to the earlier paragraph. Used to find roots, replies (`findRepliesTo`), and the whole topic branch of a paragraph — this is the basis of the spec's archive "history by topic". `Analyzer` computes unanswered questions (a question is answered by a POINTED reply or by a discussion opened from it that has a message): `conversationNotAnsweredQuestions` (all open ones, including those still waiting for a reply) and `questionsLeftUnanswered` (only those a reply skipped for good). `Conversation.questionsLeftUnansweredBy(draft, discussionId)` previews, without changing anything, what a draft would skip (for the spec's warning pop-up). `TopicHistory.of(conversation, paragraphId)` is the archive's history by topic (spec 1.3.4): the connected component, plus, from the main conversation, every paragraph of the specific discussions opened from it (in a chain).
- **Persistence** (`com.aemotionalline.infrastructure.persistence`) — the domain declares `CoupleRepository`, `NegotiationRepository`, `ConversationRepository` (plain Java) and rebuilds aggregates with `restore(...)` methods reserved to persistence (snapshots of facts only; graph, agreement, constraints in force, last senders derived). Couples and negotiations use Spring Data JDBC repositories; the conversation uses explicit SQL (`ConversationReader`/`ConversationWriter`, insert-only for append-only data, upserts for state). Write operations lock with `findByIdForUpdate` (`SELECT ... FOR UPDATE`; lock order user, couple, conversation, negotiation) and load an aggregate only after its lock (before it, only small lookups such as `findCoupleIdOf`); they run at READ COMMITTED (the pool's default), so what they read after the lock is the latest committed data, while read-only service methods use `@ReadOnlyTransaction` (REPEATABLE READ, one consistent state across their queries). The server `Clock` is UTC and ticks in microseconds (`DATETIME(6)`).
- **Constraints** (`domain.constraint`) — `Constraint.isSatisfied(ConstraintContext)`; `ConstraintAssignment` binds a constraint to a user. The conversation owns the constraint change requests: the therapist calls `proposeConstraints(therapist, assignments)` (one pending request at a time; assignees must be partners), the partners `approveConstraints(id, partner)` (the second approval applies them) or `rejectConstraints`, the therapist may `withdrawConstraints`; statuses `PENDING` -> `REJECTED`/`WITHDRAWN`/`APPLIED`; every request stays in the history as an immutable `ConstraintRequestRecord` (instants, approvals, who rejected, the constraints an applied request replaced). `getConstraintAssignments()` is a copy, so nothing outside the conversation can apply a request. `Conversation.sendMessage(message, discussionId, context)` runs every check before any change (not already sent, readiness, sender permission, discussion, turn, constraints, then `ensureValidParagraphs` for ids, references, answers, the origin rule and self-citations), then appends to the discussion and graph and seals the message. The context may be null when the sender has no constraints. Constraints have a scope (`ConstraintScope` READ/WRITE/BOTH); `Conversation.readMessage` checks READ ones and records the first read, which a reply requires. Kinds: `TimeConstraint` (time of day, WRITE by default), `ReplyDelayConstraint` (delay since the first read), `LocationConstraint` (within/beyond a radius of a `GeoPosition`, READ by default). The device constraint is dropped for now.

Code style: Allman braces, tabs/spaces mixed as in existing files. Don't re-verify a collection mutation after performing it ("add, then check it contains"): it can never fail; those checks were removed on 2026-10-05.

- **Problem found (2026-11-02), to discuss with the user before fixing:** MariaDB's default isolation is REPEATABLE READ: a transaction's **first plain read fixes a snapshot**, and every later plain read uses it, **even after a `FOR UPDATE` lock** (verified with a throwaway test: the locking read sees the new value, the plain read right after it the old one). So a write operation that reads something before taking its lock can then load a locked aggregate as it was before a concurrent change. Places: `NegotiationService.acceptProposal`, `refuseRequest`, `abandon` (they read the negotiation before locking: e.g. a conversation loaded stale and saved back could overwrite a closing accepted meanwhile), `startDiscussionNegotiation` (reads the conversation before the couple lock), `InvitationService.accept` (two partners accepting at the same moment could leave the invitation with both acceptances and no couple). The flows that lock first (sending and reading messages, closings, constraints, most negotiation steps, the new S3 code) are not affected.
- **Snapshot problem, decided (user, 2026-11-03): option A.** Write operations run at **READ COMMITTED** (every read sees the latest committed data, so "lock, then read" is always fresh); read-only operations keep **REPEATABLE READ** (a screen loads a conversation with several queries and must see one consistent state). Rule: in a write operation an aggregate is **loaded only after its lock**; before the lock only small lookups (ids, a couple's membership). Deterministic tests reproduce each case and must fail before the fix. Option B (keep REPEATABLE READ and make every flow lock first) was rejected: each future flow would have to remember it.

### Negotiation — how it works now (A5 decisions)
The stipula is a back-and-forth of the same text. `Negotiation.start(id, couple, initialProposal, clock)` requires the initial author to be a partner; the clock sets `sentAt`. Refusing = entering edit mode: `refuseProposal(user, newId)` marks the received proposal REFUSED and creates the refuser's draft (new id, author = refuser, refused text copied); every check (turn, phase, pending proposal, null/duplicate id across the whole archive) runs before any state change. `editCurrentProposal(user, text)` lets only the draft's author, on their turn, change the text (never blank). `sendProposal(user, justification)` sets justification and `sentAt`, archives the draft and clears it. `setCurrentProposal` was removed. `Proposal` setters are package-private, so archived proposals can't be rewritten from outside. Every rule violation is a `DomainException`, including null user/id/text in the action methods and, since 2026-10-29, null arguments of `start`. `getProposals()` returns an unmodifiable snapshot list (step 6c). A proposal belongs to one negotiation for its whole life (2026-10-29: `start` binds the initial proposal, `refuseProposal` binds the new draft; a proposal already bound is rejected). Since 2026-10-29 either partner can `abandon` an open negotiation (final `ABANDONED` status), and failed negotiations can be kept in the conversation's archive (`recordFailedNegotiation`). Regression tests for each case are in `NegotiationTest` (73 tests pass).

### Paragraph link rules (decided by the user, 2026-10-03)
1. A paragraph may reply to / refer to **several** earlier paragraphs, and a paragraph may be referred to by **several** paragraphs (revised by the user the same day; it replaces an earlier "at most one" decision).
2. A question can be answered **once**, by **one** POINTED paragraph; a POINTED paragraph answers **exactly one** question (decided 2026-10-03).
3. Several paragraphs of the **same reply message** may refer to the same paragraph; links may only point to the message being answered (not from later messages). Exception (2026-10-05): in the first message of a discussion opened from a paragraph, **every** paragraph must refer to that originating paragraph itself, and to nothing else, not even to other paragraphs of its topic (strict reading confirmed by the user, 2026-10-05); the topic only matters for self-citations.
4. A POINTED paragraph must always reply to at least one paragraph, and it can only refer to a question: so no POINTED in the first message of a discussion, unless that discussion's origin is a question.
5. **Reference vs self-citation (user's definition, 2026-10-05).** A *reference* is a link saying that the responder is answering that specific paragraph of the message being answered (rules 1–3 apply; it is what `ConversationGraph` walks to rebuild topics). A *citation*, better called a *self-citation* (autocitazione), is a link a user adds inside a paragraph of their reply to a paragraph **they wrote themselves** earlier, e.g. "inoltre ho già esposto le motivazioni in <link>". It is the only element of a paragraph that may point to messages earlier than the one being answered; it answers nothing, so it does not take part in topic reconstruction (graph walks and `Analyzer` ignore it) and is exempt from rule 3. Implemented so far: the cited paragraph must already be sent and written by the same sender, anywhere in the conversation. Implemented 2026-10-05 (section C, first point): it may appear in any message, and the cited paragraph must be one the sender already sent **and** belong to the topic of the citing paragraph, i.e. to the union of the branches (`findConversationBranchContaining`) of the paragraphs it references (per paragraph; spec 1.3.3: "deve appartenere esclusivamente all'argomento del paragrafo"); a paragraph without references has no topic and cannot cite. In the first message of a discussion with an origin the topic is the origin's, across discussions.

6. **Discussion origin (user, 2026-10-05).** A discussion may be opened to expand a topic exposed in a paragraph (the origin must be a paragraph already sent; the origin is optional, the conversation's first discussion has none). Topics therefore continue across discussions through the graph. If the origin is a question, any paragraph type may refer to it in that first message (the question then counts as answered by the discussion once it has a message); a POINTED there still answers it at most once. Not coded yet: replying to the origin from another discussion is not blocked (spec: pop-up on the main conversation), the request/accept flow and the title/subtitle of the discussion, and a paragraph being origin of several discussions is not limited (open question).

Rule 1 keeps `Paragraph.references` a set, so A10 stays fully relevant. Rules 2–5 need the whole discussion, so they go in `Conversation.sendMessage` (step 5, A11).
